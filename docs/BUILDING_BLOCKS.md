# Knowledge Building Blocks

The **closed enum** every note's `building_block:` frontmatter field must take.
`scripts/validate_notes.py` rejects any value outside it (rule `FM-003`).

```
concept · model · procedure · empirical_observation
argument · counter_argument · hypothesis · navigation
```

One note carries **exactly one** building block. Mixing two in a note is the
atomicity violation the digestion pipeline exists to prevent, and it is not
cosmetic: a confirming retrieval must credit the specific claim that matched,
so a note bundling several claims quietly accumulates unearned evidence.

## The eight types

| Type | Answers the question | Contains | Does **not** contain |
|---|---|---|---|
| **concept** | *What is X?* | definition, discriminating features, boundary cases, what X is **not** | procedures for using X, evidence about X's behaviour |
| **model** | *How does X relate to Y? What happens if X changes?* | structure, components, causal or compositional relations, the range over which the relation holds | step-by-step instructions, one-off observations |
| **procedure** | *How do I do X?* | ordered steps, preconditions, what breaks if a step is skipped, where it does **not** apply | why the procedure is correct, background theory |
| **empirical_observation** | *What happened?* | a specific observed event or measurement, with source, time anchor and conditions | generalisation across observations, recommendations |
| **argument** | *Why should I believe P?* | a claim, its grounds, and the warrant connecting them | the counter-case, unevidenced assertion |
| **counter_argument** | *Why might that be wrong?* | which premise or inferential step it attacks, and on what grounds | a free-standing claim with no target |
| **hypothesis** | *Might P be true?* | a testable proposition, what would falsify it, what it predicts that rivals do not | established findings, conclusions already supported |
| **navigation** | *Where do I find things?* | an index, routing table or entry point | substantive claims of its own |

## Classifying source content

| Content pattern | Building block |
|---|---|
| Definitions, terminology, "what is X" | `concept` |
| Step-by-step instructions, commands, setup | `procedure` |
| Architecture, system components, data flow, tables | `model` |
| Claims with evidence, design rationale, trade-offs | `argument` |
| Observed behaviour, metrics, examples, demos | `empirical_observation` |
| Testable predictions, experimental design | `hypothesis` |
| Limitations, risks, critiques | `counter_argument` |
| Index or routing structures | `navigation` |

Adjacent source sections sharing a building block combine into one note.
**Never mix building blocks in a single note.**

## Why the type matters beyond filing

The type is not a label applied after writing — it is chosen **first**, and it
determines what the note must retain.

An unconditioned instruction to "summarise" has no way to know which details
matter, so it deletes whatever its notion of salience does not recognise. The
reliably deleted class is **scope conditions** — preconditions, authority,
temporal anchors, applicability bounds — because those are modal qualifications
on claims rather than claims about the world, and therefore invisible to a
what-is-this-about prior.

Declaring the type first fixes that, because each type carries a **retention
contract**: the columns above are not descriptions, they are the fields that
must survive. A `procedure` that loses its preconditions is broken even if it
reads well. An `empirical_observation` that loses its time anchor cannot answer
a temporal question. A `model` that loses its range of validity over-generalises
silently.

That is why a corpus whose genre does not fit these eight types is a **finding
to report**, not a problem to force. Assigning every note to one type because
nothing else fits produces a vault that validates cleanly and carries no
structure.

## In a benchmark corpus

Encyclopedic corpora (Wikipedia-derived multi-hop benchmarks) are mostly
`concept` and `empirical_observation`, with `model` where a passage states a
relation between entities. `argument`, `counter_argument` and `hypothesis` are
rare in such corpora and their **absence should be reported rather than
manufactured** — a corpus that contains no arguments should not yield argument
notes.

`navigation` notes are generated by the ingestion, not found in the source.
